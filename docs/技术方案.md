> 对应设计：`docs/产品设计方案.md`

## 0. 技术选型总览

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.11+ | 文档处理生态最强 |
| 后端 | FastAPI | 异步/同步皆可，自动 OpenAPI |
| 前端 | HTML + CSS + 原生 JS（无构建） | 轻量，FastAPI 静态托管 |

| 存储 | 本地文件系统 + JSON 种子数据 | 无数据库 |

**MVP 设计原则**：单进程、单用户、无外部服务依赖、所有核心功能真实运行、演示数据预置保证稳定。

## 2. 前端技术方案

- **技术栈**：原生 HTML/CSS/JavaScript，无框架、无构建步骤（不引入 npm/Node 工具链）。
- **托管**：由 FastAPI `StaticFiles` 直接挂载 `frontend/`，访问 `/` 即得页面。
- **页面构成**：单页应用（SPA 由少量 JS 组织，不引路由库），三个区域：
  1. **任务输入区**：文本输入 + 文件上传 + 常用任务快捷按钮（"组卷" / "成绩分析" / "教案"）。
  2. **步骤时间线区**：实时展示 Agent 每一步（节点名、状态、工具调用、产物）。
  3. **产物区**：产物列表，点选后 iframe 预览 + 下载按钮。
- **实时通信**：原生 `EventSource` 消费 SSE（见 §21），无 WebSocket 库依赖。
- **文档预览**：
  - PDF（学情报告）→ `<iframe>` 浏览器原生渲染。
  - Word/Excel → 服务端用 Jinja2 生成对应 **HTML 预览页**，`<iframe>` 展示（见 §12）。

> 选原生 JS 的理由：MVP 交互简单、无复杂状态管理，构建工具链徒增 5 天风险；交付的仍是可运行的 Web 软件。

## 3. 后端技术方案

- **框架**：FastAPI。路由用同步 `def` 端点（FastAPI 自动投入线程池，天然适配 CPU 密集的文档生成）。
- **分层**（自顶向下，单向依赖）：

```
api/       — 路由：参数校验、任务创建、SSE、文件下载/预览
agent/     — Planner、Workflow、Executor、Tool 循环、LLM 客户端
tools/     — Tool 注册表 + 领域工具（search/generate）
services/  — 文档生成（docx/xlsx/pdf）、成绩分析、学情报告
knowledge/ — 种子数据加载（知识点/题库/预置答题）
storage/   — 文件读写、产物路径管理
config.py  — 环境变量读取
```

- **任务执行模型**：`POST /api/tasks` 返回 `task_id` 后，在**后台线程**启动 Agent 工作流；步骤事件写入**每个任务独立的内存队列**；SSE 端点从队列读取并推送。无需消息队列，进程内即完成。
- **进程模型**：单进程、单 Uvicorn worker（避免多进程下 SSE 队列/内存状态不共享的坑——演示稳定性优先）。

## 4. Agent 架构

Agent 引擎由四个组件构成：

| 组件 | 职责 | 是否调用 LLM |
|---|---|---|
| **Planner** | 解析用户意图，选择工作流并提取参数（学科/章节/题量等） | ✅ |
| **Workflow** | 预定义步骤序列，编排节点、传递中间产物 | ❌（纯编排） |
| **Executor** | 在单个节点内运行 ReAct 工具循环，驱动 LLM 调用工具 | ✅ |
| **Context** | 任务状态容器：参数、中间产物路径、步骤事件、产物清单 | ❌ |

**设计要点**：采用「**预定义工作流 + 节点内自由工具循环**」混合模型。工作流决定"做哪几步"（稳定、可预期），节点内的 Executor 决定"这一步内部怎么调用工具/怎么生成内容"（灵活、体现 Agent 智能）。

---

## 5. Tool Calling 架构

- **统一工具接口**：每个工具 = `name` + `description` + `parameters`（JSON Schema）+ `handler(params)`。
- **注册表**：`ToolRegistry` 提供 `get_schemas()`（供 LLM）与 `execute(name, params)`（供执行）。
- **两类能力明确区分**：
  - **LLM 面向工具**（交给模型自主决策调用，见 §9）：`search_knowledge_points`、`generate_questions`、`generate_diagnosis`。
  - **确定性文档服务**（由工作流按固定顺序调用，不交给 LLM 自由发挥）：`create_exam_docx`、`create_answer_sheet_xlsx`、`create_report_pdf`、`create_lesson_plan_docx`。

> 这样做的理由：文档生成参数复杂、格式敏感，交给 LLM 自由调用容易出错且不稳定；交给工作流确定性调用，既稳定又能清晰展示"编排"能力。

---

## 6. Workflow 架构

工作流 = 有序节点序列，用 Python 函数/类表达（**workflow-as-code**，不引入工作流引擎依赖）。

**英雄工作流「章节小测闭环」节点**：

```
① understand_task      — Planner 解析任务，提取 {学科, 章节, 题量, 时长, 难度}
② fetch_knowledge      — 调 search_knowledge_points 拿知识点
③ generate_exam        — Executor 调 generate_questions 生成题目(JSON)
④ build_exam_docx      — 确定性服务，生成 试卷.docx
⑤ build_answer_sheet   — 确定性服务，生成 答题卡.xlsx
⑥ load_student_answers — 加载预置答题/成绩（seed）
⑦ analyze_scores       — pandas 统计
⑧ diagnose             — Executor 调 generate_diagnosis 生成诊断文字
⑨ build_report_pdf     — 确定性服务，生成 学情报告.pdf
```

每个节点结束 → 写一条步骤事件 → 前端时间线更新。任一节点失败 → 记录失败事件，工作流终止并给出可读错误。

**第二个工作流「教案生成」**（简单，3 节点）：`understand → 生成教案正文(LLM) → build_lesson_plan_docx`。

## 7. LLM 调用方案

- **抽象层**：`LLMClient` 统一接口：`chat(messages, tools=None) -> AssistantMessage`，屏蔽不同厂商差异。
- **实现**：
  1. `ClaudeProvider`（Anthropic Messages API，工具调用 `tools` + `tool_use`/`tool_result`）——推荐，工具调用质量最高。
  2. `OpenAICompatProvider`（OpenAI 风格 `function calling`，适配 DeepSeek / Qwen / GLM）——国内可及、演示更稳的备选。
- **默认推荐**：`claude-sonnet-5`（质量优先）；若现场网络/账号不可用，切到 DeepSeek/Qwen，**只需改 `.env` 两行**（provider + model），代码零改动。
- **结构化输出策略**：不依赖 LLM 直接吐 JSON 文本（易解析失败），而是**用工具调用返回结构化参数**——`generate_questions` 的入参/出参都走 JSON Schema，天然可校验。
- **超时与重试**：单次 LLM 调用超时 60s，失败重试 2 次（指数退避），仍失败则该节点报错。

## 8. Tool 注册机制

用装饰器注册，注册表在启动时自动收集：

```
@tool(
    name="generate_questions",
    description="根据知识点生成题目，返回结构化题目列表",
    parameters={ ...JSON Schema... },
)
def generate_questions(knowledge_points: list, count: int, ...) -> dict:
    ...
```

- 装饰器把 `name/description/parameters/handler` 登记进 `ToolRegistry`。
- `ToolRegistry.get_schemas()` 拼成 LLM 所需的 `tools` 参数。
- `ToolRegistry.execute(name, params)` 校验参数 → 调用 handler → 捕获异常转为结构化错误返回给 LLM（让模型可自我纠错）。

## 10. Agent 与 Tool 的调用流程

**节点内 Executor 的 ReAct 循环（伪代码，示意）**：

```
def run_tool_loop(messages, tools):
    while True:
        resp = llm.chat(messages, tools=tools)
        if resp.has_no_tool_calls:
            return resp.text          # 最终答案
        for call in resp.tool_calls:
            try:
                result = registry.execute(call.name, call.params)
            except Exception as e:
                result = {"error": str(e)}   # 结构化错误回喂，让模型纠错
            messages.append(tool_result(call, result))
```

**整体调用链**：

```
Planner(LLM) 解析任务 → 选定工作流 + 参数
   → 工作流逐节点执行：
        节点含 LLM 工具循环 → run_tool_loop(...)
        节点是文档服务   → 直接调用 services
   → 每节点推送步骤事件(SSE)
   → 汇总产物清单 → 任务完成
```

## 11. 文件上传与文件存储方案

- **上传**：`POST /api/upload`（multipart/form-data）→ 校验扩展名（`.xlsx/.docx/.pdf`）+ 大小上限（10MB）→ 存到 `data/uploads/{task_id}/{原名}`。
- **产物**：Agent 生成的文件统一存 `data/outputs/{task_id}/`，命名规范 `{序号}_{类型}.{ext}`（如 `02_答题卡.xlsx`）。
- **无数据库**：任务元数据（task_id、状态、产物清单）保存在内存字典 + 可选落一份 `data/outputs/{task_id}/manifest.json` 便于重启后仍可查看。
- **路径安全**：所有文件路径由后端生成，不接受前端传绝对路径，杜绝路径穿越。

## 12. Word / Excel / PDF 文件生成方案

| 产物 | 库 | 方案 |
|---|---|---|
| 试卷.docx | python-docx | 统一样式函数（标题/大题/小题/选项），题干与答案分离（答案进答题卡） |
| 答题卡.xlsx | openpyxl | 表头 + 题号列 + 姓名列 + 每题分值，样式（边框/居中/列宽） |
| 学情报告.pdf | reportlab（platypus） | 标题 + 段落 + 表格 + 柱状图（`reportlab.graphics` 内置，**不引入 matplotlib**） |
| 教案.docx | python-docx | 结构化段落（教学目标/重难点/过程/作业） |

**关键约定**：文档服务接收"数据 + 结构"，样式由服务端统一控制；LLM 只负责"内容"，不负责"排版"——保证产出专业、稳定、可编辑。

## 13. 题目与知识点数据结构

**知识点（KnowledgePoint）**（对应 `data/knowledge/knowledge_points.json`）：
```json
{
  "kp_id": "kp_quad_05",
  "name": "因式分解法",
  "subject": "数学",
  "grade": "九年级",
  "chapter": "一元二次方程",
  "section": "21.2 解一元二次方程",
  "level": 2,
  "description": "利用提公因式、平方差、十字相乘等因式分解方法求解",
  "typical_types": ["填空题", "解答题"]
}
```

**题目（Question）**（对应 `data/questions/question_bank.json`）：
```json
{
  "question_id": "q9",
  "type": "解答题",
  "stem": "解方程：x² - 5x + 6 = 0。",
  "options": null,
  "answer": "x=2 或 x=3",
  "score": 12,
  "difficulty": "中等",
  "knowledge_points": ["kp_quad_05"],
  "analysis": "因式分解得 (x-2)(x-3)=0，故 x=2 或 x=3。"
}
```
- `knowledge_points` 为**知识点 ID 数组**（关联一个或多个，见附录），非知识点名称。
- 选择题有 `options`；填空/解答题 `options` 为 `null`，`answer` 存标准答案文本。

## 14. 预置种子数据总览

三个 JSON 文件构成"成绩分析 / 学情诊断"的**确定性数据源**（与 LLM 实时出卷解耦），启动时由 `knowledge/loader.py` 一次性加载进内存：

```
data/
├── knowledge/
│   └── knowledge_points.json   # 知识点（7 个，含层级/描述）
├── questions/
│   └── question_bank.json      # 规范测验（10 题，共 100 分，每题关联知识点 ID）
└── demo/
    └── student_answers.json    # 预评分答题数据（20 名学生）
```

三个文件的字段定义与 ID 关联关系见文末「附录：种子数据字段说明与关联关系」。

> 说明：`question_bank.json` 与 `student_answers.json` 共同构成"成绩分析"场景的**规范测验**——题目固定、答案确定、预评分，保证演示 100% 可复现；"智能组卷"场景则由 LLM 实时出题，两者互不依赖。

## 15. 预置学生答题数据结构

`student_answers.json` —— **预评分、确定性**，直接可分析（不依赖模糊批改）：

```json
{
  "quiz_id": "quiz_quad_01",
  "class_name": "九年级三班",
  "full_marks": 100,
  "students": [
    {
      "student_id": "s001",
      "name": "张伟",
      "question_scores": {"q1": 8, "q2": 8, "q3": 8, "q4": 8, "q5": 8, "q6": 8, "q7": 10, "q8": 14, "q9": 12, "q10": 16},
      "total": 100
    }
  ]
}
```

- 预置一个班 **20 名学生**的数据，含**人为设计的薄弱点**（q5/q8/q10 得分率低 → 对应「判别式、公式法、实际应用」薄弱），保证学情诊断演示有故事性。
- 采用"每题得分已给定"而非"原始答案+现场批改"，是为了**保证批改/分析环节 100% 确定、现场零风险**（与产品方案 §16 的"演示稳定性决策"一致）。
- `total` 为 `question_scores` 的求和（冗余字段，便于展示与校验；分析时以 `question_scores` 求和为准）。

## 16. 成绩分析算法 / 数据处理流程

用 pandas 对 `question_scores` 做确定性聚合：

```
1. 读入 student_answers → DataFrame（行=学生，列=各题得分 + total）
2. 班级指标：平均分、中位数、最高/最低、标准差、及格率(≥60%)、优秀率(≥85%)
3. 分数段分布：<60 / 60-69 / 70-79 / 80-89 / ≥90 各档人数
4. 逐题正确率：每题得分=满分 的人数 / 总人数 → 定位"低正确率题目"
5. 知识点聚合：低正确率题目 → 关联知识点 → 薄弱知识点按正确率升序排名
6. 输出结构化 stats 对象（供报告 + generate_diagnosis 使用）
```

全部为确定性计算，无随机性。

## 17. 学情诊断流程

```
分析结果(stats + 薄弱知识点)
        ↓
generate_diagnosis(LLM)：读入 stats + 薄弱知识点
        ↓
产出：班级总体小结 + 薄弱知识点诊断 + 分层教学建议（按分数段/学生分组）
        ↓
写入报告
```

诊断不改变数据，只负责"解读数据 + 给建议"，是"智慧教育"落点的关键一环（因材施教）。

## 21. Agent 执行过程实时展示方案

- **技术**：FastAPI `StreamingResponse`（`text/event-stream`）手写 SSE，**不引入 sse-starlette** 等额外依赖。
- **机制**：每个 task 一个内存 `queue.Queue`；工作流节点执行时 `put()` 步骤事件；SSE 端点循环 `get()` 并 yield，任务结束或连接断开即返回。
- **兜底**：前端 `EventSource` 断线自动重连；`GET /api/tasks/{id}` 可拉取完整状态（刷新页面后仍能看到已完成步骤）。
- 事件含：节点名、状态、文案、工具名、产物 file_id，前端据此渲染时间线。

## 22. 错误处理与超时处理

| 场景 | 处理 |
|---|---|
| LLM 调用超时/失败 | 60s 超时 + 重试 2 次（退避）；仍失败 → 节点标 ❌，任务终止并给可读错误 |
| LLM 返回无法解析的 JSON | 走工具 schema 校验，不合规 → 回喂错误让模型重试（最多 3 次） |
| 工具执行异常 | 捕获 → 返回 `{"error": ...}` 给 LLM 自纠；不可恢复 → 节点失败 |
| 全局任务超时 | 整条工作流 180s 上限，超时强制结束并给提示 |
| 文件缺失 / 种子数据缺失 | 启动时校验 seed 完整性，缺失即启动失败并给出明确日志 |
| 前端 SSE 断连 | EventSource 自动重连；状态可随时由 REST 拉取兜底 |

**核心原则**：任何失败都要**在时间线上可见、给人类可读原因**，演示时"失败但能解释"远好于"黑盒卡死"。

## 附录：种子数据字段说明与关联关系

### 文件 1：`data/knowledge/knowledge_points.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `subject` / `grade` / `chapter` | string | 学科 / 年级 / 章节 |
| `chapter_id` | string | 章节 ID（`ch_quad_01`） |
| `knowledge_points[]` | array | 知识点列表 |
| `knowledge_points[].kp_id` | string | 知识点唯一 ID（`kp_quad_XX`），被题目关联 |
| `knowledge_points[].name` | string | 知识点名称 |
| `knowledge_points[].level` | int | 层级：1 基础 / 2 核心（解法）/ 3 应用 |
| `knowledge_points[].section` | string | 教材节次 |
| `knowledge_points[].description` | string | 知识点描述 |
| `knowledge_points[].typical_types` | array | 该知识点常见题型 |

### 文件 2：`data/questions/question_bank.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `quiz_id` | string | 测验 ID（`quiz_quad_01`），被答题数据引用 |
| `title` / `subject` / `grade` / `chapter` | string | 测验元信息 |
| `chapter_id` | string | 章节 ID |
| `total_score` | int | 总分（= 各题 `score` 之和，100） |
| `questions[]` | array | 题目列表 |
| `questions[].question_id` | string | 题目 ID（`q1`..`q10`），被答题数据引用 |
| `questions[].type` | string | 选择题 / 填空题 / 解答题 |
| `questions[].stem` | string | 题干 |
| `questions[].options` | array \| null | 选择题选项；其余为 `null` |
| `questions[].answer` | string | 标准答案 |
| `questions[].score` | int | 该题满分 |
| `questions[].difficulty` | string | 简单 / 中等 / 较难 |
| `questions[].knowledge_points` | array | **关联的知识点 `kp_id` 列表（≥1）** |
| `questions[].analysis` | string | 解题解析 |

### 文件 3：`data/demo/student_answers.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `quiz_id` | string | 引用的测验 ID（= 题库 `quiz_id`） |
| `class_name` | string | 班级名称 |
| `full_marks` | int | 满分（100） |
| `students[]` | array | 学生列表 |
| `students[].student_id` / `name` | string | 学生 ID / 姓名 |
| `students[].question_scores` | object | 每题得分，键为 `question_id`，值为得分 |
| `students[].total` | int | 总分（= `question_scores` 求和，冗余便于校验） |

### ID 关联关系

```
knowledge_points.json
   kp_id ────────────────────┐
                             │ (knowledge_points[] 引用)
question_bank.json           │
   quiz_id ◄────┐            │
   question_id ◄─┐           │
                 │           │
student_answers.json
   quiz_id ──────┘
   question_scores 的键 ──► question_id（每题得分 ≤ 该题 score）
```

**约束**：
1. 题目的每个 `knowledge_points` 值必须存在于知识点文件。
2. 答题数据的 `quiz_id` 必须与题库一致。
3. 答题 `question_scores` 的键集合 = 题库 `question_id` 集合，且每题得分 ≤ 该题 `score`。
4. `students[].total == sum(question_scores.values())`。
5. 全部文件为合法 UTF-8 JSON，可由 `json.load` 直接读取。

## 最终结论（A–F）

### A. 系统架构图
见 §1：单进程 FastAPI（API + Agent 引擎 + 工具层 + 文档服务层）+ 本地文件系统（seed JSON + 产物），无 DB/队列/容器。

### B. Agent 执行流程图
见 §6 / §10：`Planner(LLM) 解析 → 工作流 9 节点（LLM 工具循环与确定性文档服务交替）→ 每节点推送 SSE → 交付产物清单`。

### C. Tool 列表及 JSON Schema
- LLM 面向工具（3）：`search_knowledge_points`、`generate_questions`、`generate_diagnosis`（完整 Schema 见 §9）。
- 确定性文档服务（4）：`create_exam_docx` / `create_answer_sheet_xlsx` / `create_report_pdf` / `create_lesson_plan_docx`（工作流调用，见 §9 表）。

### D. API 接口表
见 §19：`POST /api/tasks`、`GET /api/tasks/{id}`、`GET /api/tasks/{id}/events`(SSE)、`POST /api/upload`、`GET /api/files/{id}`、`GET /api/preview/{id}`、`GET /api/health`。

### E. 项目目录结构
见 §25：`backend/`（api / agent / tools / services / knowledge / storage）+ `frontend/`（原生三件套）+ `docs/` + `data/`。

### F. MVP 开发顺序
